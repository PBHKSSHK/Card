# CardRecon — Full Audit (2026-08)

Two independent methods, cross-checked:

- **Live backend probes** — 5 disposable principals (owner / admin / 3 scoped
  bu_users) exercised the *real* RLS policies via `request.jwt.claims` +
  `set role authenticated`, i.e. exactly how PostgREST evaluates them. ~50
  scenarios across two batches.
- **Parallel code audit** — 8 subsystem readers generated 122 scenarios and 73
  findings; every high/critical finding was then handed to an adversarial
  verifier that tried to refute it against the source. 19 confirmed, 2 refuted.

170 scenarios total.

## NetSuite sync

The app has **no direct NetSuite write path** — no SuiteTalk / RESTlet / token
auth anywhere; the server exposes only `/api/health`. The only outbound route
is a **CSV download** that a human imports into NetSuite, so posting is
inherently human-gated.

Caveat found & fixed: the bulk Claim Journal Export query previously included
`team_head_approved` batches, so claims that only had a team-head signature
(not final approval) could be posted, bypassing the last checkpoint. Now
restricted to `approved` / `exported`.

## Core security model — verified sound

Confirmed working by live越權 attempts:

- Entity-scope isolation on `meta_invoices` / `accounting_lines` (CLS user
  cannot see PBHK data, etc.).
- No privilege escalation: a bu_user cannot change their own role/scope, nor
  edit another user's profile.
- Claim privacy + state machine: claimants can't approve their own claims,
  can't skip steps, can't see colleagues' claims; team-head approval path
  works; cross-user approval blocked.
- Anonymous role has no table grants at all (defense-in-depth above RLS).
- Storage receipts are isolated per `{uid}/` folder.
- Integrity constraints (claim_type / status CHECK, unique account_number,
  total recompute triggers) all hold.

## Findings & disposition

### Fixed in migration `00000000000011_security_hardening_2.sql` (applied live + verified)

| # | Finding | Fix |
|---|---------|-----|
| 1 | `ns_*` master data (chart of accounts, subsidiaries, departments, employees, vendors, customers, cc accounts, project codes) writable/deletable by any authenticated user | write → `is_super_user()`; read stays open |
| 2 | Global `journal_settings` writable by any authenticated user | update → `is_super_user()` |
| 3 | `bank_transactions` / `ns_gl_entries` / `bank_recon_results` readable by every authenticated user across all subsidiaries | SELECT → `is_super_user()` (only the SuperOnly `/bank-recon` page reads them, so zero regression) |
| 4 | Storage policies had an `or foldername = 'claims'` escape hatch letting any user read/write/delete under `claims/*` | branch removed (app only ever uses `{uid}/`, so dormant — no data was exposed) |

Post-fix probes: bu_user now reads 0 bank/GL rows (was 715 / 497); admin still
reads all; bu_user master-data/settings writes blocked; admin writes and normal
reference reads + matching-rule writes all still work.

### Fixed in frontend

| Finding | Fix |
|---------|-----|
| FX fetch failure / unsupported currency silently left `fx_rate = 1`, booking foreign spend at 1:1 | changing currency now clears rate+HKD and refetches; a failed fetch forces manual entry |
| Currency change recomputed HKD with the *previous* currency's stale rate | same fix — rate is cleared then refetched on every currency change |
| Reconciliation engine loaded `card_transactions` / `meta_invoices` unbounded, silently truncating at PostgREST's 1000-row cap | paginated with `.range()` until a short page |
| Bulk journal export posted `team_head_approved` (not finally-approved) claims | eligibility restricted to `approved` / `exported` |

### Deliberately left as-is (documented decisions, not oversights)

- **`matching_rules` writable by any authenticated user** — the Assign
  "save as rule" flow and bulk import are used by ordinary finance staff.
  Locking to admin would break a live feature; threat model is 16 trusted staff.
- **`reconciliation_results` SELECT open to authenticated** — the `/recon` page
  is not SuperOnly and legitimately needs match status; its WRITE is already
  entity-scoped.
- **`card_transactions` / `upload_batches` INSERT `WITH CHECK (true)` + null-owner
  visibility** — no row currently has a null owner, so nothing leaks; tightening
  would break client insert paths that legitimately omit `user_id`.
- **Journal-export idempotency (no auto-lock after export)** — flagged; whether
  export should auto-transition batches to `exported` is a workflow decision for
  the finance team (they may rely on re-export), so left unchanged.

### Refuted by adversarial verification (not real)

- "Split accounting_lines never reconciled to transaction total on export."
- "No unique constraint on `reconciliation_results.transaction_id` allows dup rows."
